# Модуль «Склад» — дизайн

Дата: 2026-07-07
Статус: утверждён пользователем, ожидает implementation plan

## Контекст

В хабе ERP (`app/pages/register.vue`) плитка «Склад» помечена «В разработке» и ведёт на пустой `app/pages/warehouse.vue`. Задача — реализовать полноценный функционал приёма/выдачи/остатков товара со склада.

Источник данных — отдельная Google-таблица (НЕ «Ведомости»):
`https://docs.google.com/spreadsheets/d/<WAREHOUSE_SPREADSHEET_ID>`

Листы: «Склад», «Лог», «Номенклатура» (в задаче также есть «Заявки» и «Согласования» — вне скоупа этой спеки, для будущих вкладок «Снабжение»/«Согласования»).

## Реальная структура листов (проверено вживую в таблице)

**Номенклатура** — 2 колонки:
| A: Наименование товара | B: Категория |

Единицы измерения в номенклатуре нет — вводится вручную на экранах Приёма/Выдачи.

**Лог** — колонки A–M:
| A Дата | B Площадка | C Действие | D Ячейка хранения | E Наименование | F Тип | G Категория | H Кол-во | I Ед.изм. | J Принял | K Выдал | L Получил | M ID |

**Склад** — колонки A–J, это агрегирующий отчёт, каждая строка — уникальная комбинация `Площадка+Ячейка+Наименование+Тип+Категория`:
| A ID | B Площадка | C Ячейка хранения | D Наименование | E Тип | F Категория | G Поступление | H Выдача | I Остаток | J Ед.изм. |

Формулы `Поступление`/`Выдача` в «Склад» — `=СУММЕСЛИМН(Лог[Кол-во];Лог[ID];A2;Лог[Действие];"Прием"|"Выдача")`, `Остаток = Поступление - Выдача`. Строки в «Склад» **статичны** — нет скрипта, который добавлял бы их автоматически при появлении нового ID в «Лог» (см. решение ниже).

**Формат ID** (подтверждено по реальным данным, 5 частей, не 4 как в исходном ТЗ):
```
Площадка|Ячейка хранения|Наименование|Тип|Категория
```
Пример из таблицы: `Колпино|1|Аккум. батареи|Новый|Канцелярия`

## Ключевые решения (из уточняющих вопросов)

1. **ID — 5 частей с Категорией** (как в реальных данных). Категория для ID подтягивается из «Номенклатура» по выбранному наименованию — сама колонка «Категория» в «Лог» при этом не заполняется, как и просил пользователь.
2. **Новый ID в «Склад» — GAS создаёт строку автоматически.** Если при Приёме получившийся ID не находится среди строк «Склад», скрипт вставляет новую строку (Площадка/Ячейка/Наименование/Тип/Категория + формулы Поступление/Выдача/Остаток, скопированные с соседней строки) перед записью в «Лог».
3. **Единица измерения — короткий фиксированный список**: `шт.`, `пар`, `кг`, `м`, `компл.` (chip-выбор, не свободный текст).
4. **Бэкенд — новый отдельный standalone GAS-проект** «Склад», отдельные Deployment ID/URL, отдельная env-переменная `NUXT_PUBLIC_WAREHOUSE_GAS_URL`. Та же архитектурная логика, что уже применена к ERP Ведомости vs FindTagMFT — разные бизнес-домены не должны жить в одном скрипте/деплое.

## Архитектура

### Бэкенд: `scripts/warehouse-gas-webapp.js`

Новый standalone GAS-проект, создаётся через `clasp create --type standalone`, деплой/тест — тот же процесс, что уже обкатан для «ERP Ведомости» (staging-копия таблицы + staging GAS-проект → полный прогон → прод).

**GET-экшены:**
- `?action=categories` — уникальные значения колонки «Категория» из «Номенклатура»
- `?action=items&category=X` — «Наименование товара» из «Номенклатура», отфильтровано по категории (для Приёма — весь ассортимент, без проверки остатка)
- `?action=stock&category=X&platform=Y` — строки «Склад» по `Площадка=Y` (+ `Категория=X`, если передана — для Баланса категория не передаётся) и `Остаток > 0`

**POST-экшены:**
- `receiveItem {platform, cell, name, type, qty, unit, fio}` → строит ID (категория ищется на сервере по `name` в «Номенклатура»), при отсутствии строки в «Склад» — добавляет её, затем `appendRow` в «Лог» (`Действие="Прием"`, `Принял=fio`, `Выдал`/`Получил` не трогаются, `Категория` не заполняется)
- `issueItem {platform, cell, name, type, qty, unit, fio, recipientFio}` → `cell` приходит с фронта (пользователь выбрал конкретную строку остатка из списка), а `type`/`unit` — **редактируемые поля формы**, как и в исходном ТЗ (пользователь может выдать не тем типом/ед.изм., что был показан в списке). Сервер пересобирает ID из **финальных отправленных** `type`/`unit` (не из значений исходно выбранной строки) и ищет по этому ID строку в «Склад» — если такой ID не находится, остаток считается 0 (а не ошибка «не найдено»), запрос естественно отклоняется проверкой `qty <= Остаток`. Так на сервере всегда списывается именно та позиция, которую реально отправила форма — без риска разъехаться с «Складом».

Конкурентность — `LockService.getScriptLock()`, тот же паттерн, что в `erp-gas-webapp.js`.

### Фронтенд

Роуты — **плоские имена** (как везде в кодовой базе: `/scan-measurement`, `/handover-shift`, а не вложенные папки):
- `/warehouse` — хаб: 3 кнопки-действия (Приём/Выдача/Баланс), замена текущей заглушки
- `/warehouse-receive` — плитки категорий → список наименований + `ErpSearchBar`, тап по товару сохраняет его имя в `erp-session.store.ts` и ведёт на `/warehouse-receive-form`
- `/warehouse-receive-form` — отдельный экран (по образцу `measurement.vue`): Количество/Ед.изм. (chips)/Ячейка хранения/Тип (toggle) → «Принять»
- `/warehouse-issue` — то же, но список строится напрямую из строк `?action=stock` (остаток > 0 для площадки сотрудника), а не из уникальных наименований: если один товар/тип лежит в нескольких ячейках, каждая ячейка — отдельная строка списка (подпись показывает номер ячейки и остаток именно в ней). Тап сохраняет всю строку (`cell`, `type`, `unit`, `balance`) в сторе и ведёт на `/warehouse-issue-form`
- `/warehouse-issue-form` — Количество/Ед.изм. (chips, предзаполнено из выбранной строки, редактируемо)/Тип (toggle, предзаполнено, редактируемо)/ФИО получателя → «Выдать»
- `/warehouse-balance` — таблица (Категория/Наименование/Остаток/Ед.изм.), read-only, без действий

`ErpActionSheet` **не переиспользуется** — его слоты (`content`/`meta`) рассчитаны на одну строку текста для подтверждения (как в `ErpBadgeConfirmSheet`), а не на форму с несколькими полями. Вместо него — отдельные экраны-формы, ровно по паттерну `scan-measurement.vue → measurement.vue`, уже существующему в кодовой базе.

Новый `app/utils/warehouse-sheets.ts` (аналог `erp-sheets.ts`). Новый `app/components/warehouse/WarehouseCategoryGrid.vue` (общая сетка плиток категорий для Приёма и Выдачи — идентичная разметка, разный обработчик клика). Транзитное состояние выбора — в `erp-session.store.ts` (те же поля рядом с `selectedBadge`/`measurementBadge`). `access.warehouse` — уже существующий флаг в `ErpAccessFlags`, новый не нужен.

**Middleware:** `erp-flow.global.ts` — `/warehouse` уже в `ACCESS_GUARDED` → `'warehouse'` (проверено, было добавлено раньше вместе с остальными флагами). Новые `/warehouse-receive`, `/warehouse-receive-form`, `/warehouse-issue`, `/warehouse-issue-form`, `/warehouse-balance` добавляются туда же + в `ERP_ROUTES`. Плюс два guard'а по образцу `/receipt`: `/warehouse-receive-form` без выбранного товара → редирект на `/warehouse-receive`, `/warehouse-issue-form` без выбранной строки → редирект на `/warehouse-issue`.

## Обработка ошибок и граничные случаи

- Списки категорий/наименований — Loading / Error+«Повторить» / «Ничего не найдено», как в `badges.vue`.
- Приём: количество — обязательное целое > 0 (валидация как в `measurement.vue`), ячейка хранения — обязательное непустое поле.
- Выдача: количество не может превышать Остаток **той позиции, что реально получится из отправленных type/unit** (см. выше) — проверка на клиенте по исходно показанному остатку (для быстрой UX-подсказки) и обязательно на сервере против пересчитанного ID (источник истины, защита от гонки и от смены типа/ед.изм. на форме).
- ФИО получателя — обязательное текстовое поле, без валидации против реального списка сотрудников (как указано в ТЗ).

## Тестирование

Тот же процесс, что и с ERP Ведомости в этой сессии: staging-копия таблицы «Склад» + отдельный staging GAS-проект → полный прогон всех экшенов (включая создание новой ID-комбинации и access-guard) → только затем прод-деплой с сохранением Deployment ID.

## Вне скоупа этой спеки

- Листы «Заявки», «Согласования» в этой же таблице — для будущих вкладок «Снабжение»/«Согласования», не трогаем.
- Реальный список сотрудников для валидации «ФИО получателя» — не запрашивалось.
