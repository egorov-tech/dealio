# Грабли этого проекта

Каждый пункт — реальная ошибка, которая стоила времени. Прочитай перед правкой
фронта или деплоя: почти все они выглядят как «работает», пока не посмотришь
внимательнее.

---

## Мобильный фронтенд

### `<input type="number">` через `v-model` отдаёт число, а не строку

Вызов строкового метода на нём роняет **весь экран** — Vue выбрасывает ошибку в
`computed`, и страница белеет. Пустое поле при этом даёт пустую строку, так что
тип честно `string | number`.

```ts
// Так падало
Number(row.quantity.replace(',', '.'))

// Так правильно
typeof value === 'number' ? value : Number(String(value).replace(',', '.'))
```

Контрактные тесты это не ловят — они читают исходник. Ловится только кликом.

### Поля ввода принудительно 16px, и это не случайность

`app/assets/css/erp-theme.css` держит `.erp-layout input { font-size: 16px !important }`.
iOS Safari зумирует страницу при фокусе на поле с меньшим размером. Своё
`font-size` в компоненте **не применится** — правило с `!important` его перебьёт,
и файл будет показывать размер, которого в браузере нет.

Уменьшать можно только `::placeholder`: зум зависит от размера самого поля.

### `mousedown` не работает по касанию

На тач-устройстве mouse-события синтезируются **после** `blur`. Если по blur ты
снимаешь выпадающий список с DOM, тап по нему уходит в пустоту. Внутри
прокручиваемого списка браузер может вообще не прислать `mousedown`, посчитав
касание скроллом.

Используй `@pointerdown.prevent` — он приходит сразу по касанию, до blur, и
`.prevent` сохраняет фокус в поле.

### `v-model` не годится для поля живого поиска

Клавиатура iOS с автоподсказками держит ввод в состоянии **композиции**, пока
пользователь не уберёт её или не тапнет мимо. `v-model` по замыслу игнорирует
`input` во время композиции, поэтому модель не обновляется — список не
фильтруется, пока клавиатура открыта.

Хуже того, `compositionend` приходит **ровно в момент тапа** мимо поля: модель
обновляется, список перерисовывается, и элемент под пальцем исчезает раньше, чем
до него дойдёт событие выбора. Со стороны это два разных бага, а причина одна.

Для строки поиска композиция ничего не даёт: читаем значение напрямую.

```html
<!-- Было: фильтр молчит, пока открыта клавиатура -->
<input v-model="row.name">

<!-- Стало -->
<input :value="row.name" @input="onNameInput(row, $event)">
```

### `preventDefault` на `pointerdown` отменяет прокрутку

Обратная сторона предыдущего пункта. Если повесить выбор на
`@pointerdown.prevent`, список перестаёт листаться пальцем: браузер считает, что
жест забрал обработчик.

Развязка — не отменять ничего, а решать по самому касанию. Запомнить `clientY`
на `touchstart`, на `touchend` сравнить: палец не сдвинулся — это выбор,
сдвинулся — это прокрутка, и мы не вмешиваемся. `touchend` приходит на тот же
элемент, где началось касание, поэтому сдвиг вёрстки от закрывшейся клавиатуры
не мешает. На `touchend` нужен `preventDefault`, иначе синтетический `click`
выберет позицию второй раз.

### Выпадающий список — сосед поля, а не его потомок

Проверка «касание вне элемента» по самому полю считает тап по позиции касанием
снаружи и закрывает список раньше, чем срабатывает выбор. Проверять нужно по
области, которая содержит и поле, и список.

### Поле с уже выбранным значением нужно выделять при фокусе

Тап ставит курсор туда, куда попал палец. Если в поле уже лежит полное название,
набор дописывается в середину: «Перчатки х/бкруг» — совпадений ноль. Со стороны
выглядит как «подсказки не работают».

`event.target.select()` на фокусе: первый же символ заменяет старое значение.

### Экранная клавиатура не уменьшает обычный viewport

Список, отрисованный под полем, физически оказывается за клавиатурой:
пользователь видит его только убрав её. Считай доступную высоту по
`window.visualViewport`:

```ts
const available = viewport.offsetTop + viewport.height - rect.bottom - 12
```

и пересчитывай на `resize`/`scroll` этого объекта. Рабочий пример —
`app/pages/supply.vue`.

### Закрытие по `blur` покрывает не все случаи

Список можно открыть кнопкой, не ставя фокус в поле, — тогда `blur` не придёт
вовсе. Нужен обработчик касания вне элемента на `document`.

### Scoped-стили не достают до содержимого слота

Стили компонента-обёртки не применяются к разметке, переданной страницей в
`<slot>`. Нужен `:deep()`. Симптом бывает неочевидным: однажды это выглядело как
слипшееся «0бирок за смену».

## Бэкенд и база

### Каталог миграций ровно один

`public/api/migrations/`. Когда-то их было два, они разошлись, и на чистой базе
не создавалась таблица, в которую код писал. Второй каталог и разрывы в
нумерации ловит `tests/migrations-single-source-contract.test.mjs`.

На сервере такая копия однажды завелась в `erp-ops/` и отстала на пять файлов:
`sql-migrate.php` отчитывался по ней, а применялись совсем другие файлы. Копию
удалили, а `erp_cli_migrations_dir()` теперь выводит каталог из `ERP_API_SRC` —
то есть из того же места, откуда его берёт рантайм. Не создавай её заново.

### Имя таблицы на стенде может быть уже занято, и `IF NOT EXISTS` об этом промолчит

Базу стенда правят не только миграции: часть таблиц и колонок завели прямо на
сервере, мимо git. На 14.09.2026 там были `erp_ed`, `erp_ks`, `erp_platforms`,
`erp_report_month` и колонки `contract_name`/`prepayment`/`cost`/`ks`/`ed` в
`erp_contracts`, которых нет ни в одной миграции.

Раздел «ПТО» взял очевидные имена `erp_ed` и `erp_ks`. Имена оказались заняты
таблицами с другой схемой — `CREATE TABLE IF NOT EXISTS` ничего не создал и не
пожаловался, миграция записалась как применённая, а оба экрана отдавали 500 на
каждом запросе. Ведомость работ из той же задачи работала: её имя было
свободно.

Поэтому:

* перед новой миграцией сверяй имена с **реальной** схемой стенда
  (phpMyAdmin из ISPmanager, база `u3616626_Morflot.tech`), а не с каталогом
  миграций — репозиторий не источник правды о базе стенда;
* бери имя с префиксом раздела (`erp_pto_ed`), а не общее слово;
* чужие таблицы не переименовывай и не удаляй — их наполняет живой процесс.
  Если данные нужны разделу, копируй их один раз в свою пустую таблицу.

### Диагностика «раздел отдаёт 500» начинается с входа, а не с кода

Если `GET /api/auth/me` без сессии отвечает **401**, значит `erp_apply_migrations`
отработал без исключения: упавшая миграция роняет 500 на *любой* ручке, включая
вход. Это отсекает «миграция падает» за один запрос, без доступа к серверу.
**404** вместо 401 — маршрута нет, то есть не доехал деплой.

Контрактные тесты этот класс ошибок не ловят: они проверяют текст исходников, а
не форму таблицы. Проверяй на временной MySQL (`docs/onboarding/02-локальный-стенд.md`).

### Миграции применяет соединение, а не обработчик

`erp_database()` вызывает `erp_apply_migrations()` при создании PDO. Раньше
вызов стоял внутри отдельных разделов, и новый раздел получал схему только
потому, что пользователь успевал открыть задевающий его экран.

Не добавляй новых вызовов по месту — это ровно тот путь, который уже сломался.

### Раннер миграций делит файл по точке с запятой вне строк и комментариев

Наивный `explode(';')` разрывал файл по «;» внутри комментария: первая половина
миграции применялась, вторая падала, миграция не записывалась как применённая —
и повторный запуск спотыкался уже об «Duplicate column name». DDL в MySQL
коммитится неявно, откатить середину нельзя, и база оставалась в состоянии, из
которого не выбраться без ручной правки.

Сейчас разбор идёт посимвольно (`erp_migration_statements`), а ошибка называет
файл и номер выражения. Если добавляешь миграцию — проверь `npm run test:php`,
там есть проверка, что каждое выражение каждой миграции исполняемо.

### Значения из выгрузки несут невидимый `\r`, и diff-уведомления принимают его за событие

Импортированные строки ИД приехали со статусом `"Нет ПОЗ\r"` — в выгрузке
остались концы строк. На экране разницы не видно, но уведомления ловят событие
по расхождению `status <> notified_status`: первая же правка такой записи
выглядела бы сменой статуса, и отдел получил бы уведомление о том, чего не
было. Справочник статусов при этом показывал бы один статус дважды.

Нормализуй значение в коде — и при сравнении, и на выдаче (`erp_pto_clean`,
`ERP_PTO_STATUS_CHANGED` в `Pto.php`). Массовый `UPDATE` по живым данным чинит
только то, что уже лежит в базе, и не спасает от следующей выгрузки.

### Справочник статусов из ТЗ может не покрывать данные

У КС в ТЗ два статуса, «Подписана» и «Согласована», а в базе живёт ещё
«На согласовании». Со справочником-только-из-ТЗ такую запись нельзя сохранить
даже после правки одной суммы: валидация отклонит её собственный статус.
Объединяй список из ТЗ с теми значениями, что реально встречаются в таблице.

### Уникальный индекс нужно ловить, даже если перед вставкой есть проверка

`SELECT ... WHERE name = ?`, а следом `INSERT` — это две операции, между
которыми успевает вклиниться чужой запрос. Проверка отсеивает обычный случай, но
одновременные запросы доходят до вставки, и уникальный индекс отдаёт
`PDOException`: пользователь видит 500 «ERP временно недоступна» вместо внятного
«уже есть».

Лови `SQLSTATE 23000` и отвечай тем же 409, что и проверка. Десять параллельных
добавлений одного имени должны давать один 200 и девять 409.

### Переименование позиции справочника тянет за собой склад

Остаток лежит строкой с составным ключом
`площадка|ячейка|наименование|тип|категория`, а лог движений ссылается на тот же
ключ. Переименовать позицию в `erp_warehouse_items` и не тронуть склад — значит
оторвать остатки: они есть у 271 позиции из 301.

`erp_supply_work_update_item()` переносит имя, категорию и единицу на
`erp_warehouse_stock` и `erp_warehouse_log` в одной транзакции и пересобирает
ключи. Это **единственное** место, где лог правится, а не пополняется, — и
строка переписывается целиком: половинчатая правка оставила бы запись, где ключ
от одного товара, а наименование от другого.

### Запрет на удаление считай по остатку, а не по наличию складской строки

У списанной позиции строка в `erp_warehouse_stock` остаётся навсегда — с нулём и
историей движений. Запрет «нельзя удалить, пока есть складская строка» отвечал бы
«сначала спишите остатки» тому, кто уже всё списал, и позицию стало бы не убрать
никогда. Считай `balance <> 0` по `erp_warehouse_balance`.

### Право на разделе — не то же самое, что право на уведомление

`push/subscribe` требовал право «Согласования». Подписаться мог только тот, кто
утверждает счета, — и рассылка «всем» доходила до трёх человек из всей
компании, а уведомление о смене статуса заявки не получал её автор, то есть
человек, ради которого оно и заводилось.

Уведомление приходит человеку про его собственную работу. Что именно слать,
решает отправитель; ручке подписки достаточно того, что сотрудник вошёл.

### Подписку нужно восстанавливать при каждом входе

Подписка живёт не вечно: браузер меняет адрес доставки, push-сервис отзывает
протухший, человек переустанавливает приложение. Пока она заводилась только на
одном экране и только по кнопке, потерявший её сотрудник замолкал навсегда —
вернуть было нечем, и снаружи это выглядело как «пуш не работает».

`erp-init.client.ts` переподписывает любого вошедшего молча. Разрешение при
этом не запрашиваем: спросить может только страница по нажатию человека,
браузер сам не спросит никогда.

### «Принято push-сервисом» — это не «показано человеку»

Apple и FCM отвечают успехом и для устройства, где уведомления потом выключили.
Счётчик отправленных ничего не доказывает. На каждую отправку заводится строка
в `erp_push_deliveries` с одноразовым токеном; воркер возвращает его после
`showNotification`, и в отчёте появляется вторая цифра — сколько показано.

Первая рассылка после выкатки нового воркера подтверждений не даст: на
устройствах ещё крутится прежний, а обновляется он, когда человек откроет
приложение.

### Badging API живёт на navigator, а не на registration

`'setAppBadge' in self.registration` — всегда ложь: у `ServiceWorkerRegistration`
такого метода нет. Значок непрочитанного из-за этого не ставился ни разу ни на
одном устройстве. Правильный вызов — `navigator.setAppBadge()`, и он же с самого
начала стоял в `app/utils/erp-app-badge.ts`.

### Именованный параметр PDO нельзя переиспользовать

`PDO::ATTR_EMULATE_PREPARES => false` включён, поэтому
`SET x = :status WHERE y = :status` падает с `Invalid parameter number`. Дай
двум местам разные имена, значение подставь одно.

### Номер записи — атомарным счётчиком, не `MAX+1`

Два сотрудника, нажавшие кнопку одновременно, прочитают одинаковый максимум и
получат один номер. Рабочий приём — отдельная таблица-счётчик и
`INSERT ... ON DUPLICATE KEY UPDATE last_seq = last_seq + 1` внутри транзакции:
она же сериализует одновременные попытки.

При переносе существующих данных счётчик нужно **проинициализировать**, иначе
первая же новая запись столкнётся с импортированной.

## Загрузка файлов

### Хостинг даёт 2 МБ на файл

`upload_max_filesize = 2M`, `post_max_size = 8M` — меньше типичного скана счёта.
Поднимается через `public/api/.user.ini` (его читает PHP-FPM/CGI). Не забудь, что
`.user.ini` Apache сам **не** прячет, в отличие от `.ht*` — его надо закрыть
правилом в `.htaccess`, иначе настройки PHP качаются по HTTP.

Реальный предел всегда спрашивай у сервера и отдавай клиенту: локальный
`php -S` игнорирует `.user.ini`, и захардкоженное значение будет врать.

### Превышение `post_max_size` выглядит как «файл не приложили»

PHP отбрасывает и тело, и `$_FILES` ещё до кода. Признак — пустые `$_POST` и
`$_FILES` при ненулевом `CONTENT_LENGTH`; без явной проверки пользователь видит
«прикрепите файл» на файле, который только что прикрепил.

### `Content-Type: application/json` ломает multipart

`FormData` сам несёт заголовок с `boundary`. Подставленный поверх JSON-заголовок
означает, что файл до сервера не доедет вовсе. И таймаут: 8 МБ по мобильной
связи не влезают в общие 12 секунд.

## Деплой

### CI выкладывает только `.output/public`

Всё из `public/` попадает на сервер, а `scripts/` — **нет**. Серверные CLI-скрипты
живут в `erp-ops/scripts` и заливаются вручную по FTP. Если правил скрипт —
проверь, что на сервере лежит та же версия: они молча расходятся.

### `upload-artifact` по умолчанию выбрасывает точечные файлы

`include-hidden-files: false` — значение по умолчанию у v4. Из-за этого
`public/api/.htaccess` не выкладывался ни разу, API работал на копии от ручной
заливки, и первая же правка в нём молча ушла в никуда. В workflow теперь стоит
`include-hidden-files: true` и проверка, что файл есть в сборке.

### «Деплой успешен» ≠ «выложилось то, что нужно»

Раньше это значило только «scp не упал». Теперь после выкладки CI сверяет
`release.txt` с текущим коммитом и проверяет, что внутренности API отдают 404.
Не убирай этот шаг.

### Всё под `public/` доступно по HTTP

Исходники API, миграции со схемой базы, `composer.json` лежат в webroot.
Закрывает их `public/api/.htaccess` — правилами, которые стоят **выше**
правила, пропускающего существующие файлы. Порядок здесь и есть защита.

### Режим бэкенда задаётся окружением

`NUXT_PUBLIC_ERP_BACKEND_MODE` берётся из переменной GitHub Environment. Пока
её не передавали в сборку, каждый деплой через CI молча возвращал стенд на GAS,
хотя SQL-сборку туда выкладывали руками.

## Локальная разработка

### MySQL на macOS: путь к сокету не длиннее 103 символов

Временный экземпляр в глубокой временной папке не поднимется. Клади сокет в
`/tmp/<короткое-имя>.sock`.

### `php -S` без воркеров вешает браузер

Однопоточный сервер не отдаёт ассеты параллельно с keep-alive-соединением:
страница загружается вечно. Нужен `PHP_CLI_SERVER_WORKERS=8`.

### `php -S` требует `-t` на каталог сборки

Иначе `return false` в роутере ищет статику относительно рабочего каталога, и
всё отдаёт 404 при живом сервере.
