## 1. Первые пять минут

```bash
npm ci
npm run verify        # контрактные тесты + PHP-тесты + типы + линт
```

`npm run verify` обязан быть зелёным **до** твоей правки. Если он красный на
чистом дереве — это отдельная проблема, чини её раньше своей задачи и скажи

## 2. Что это за продукт

Внутренняя ERP для промышленного заказчика (антикоррозионная защита, изоляция,
судоремонт). **Основной пользователь — мастер в цеху с телефоном в руке**, часто
в перчатках. Отсюда всё остальное: крупные зоны нажатия, минимум ввода с
клавиатуры, ничего не теряется при плохой связи.

- Прод: <https://erp-mt.ru> — **трогать нельзя без отдельного разрешения**
- Стенд: <https://erp-mt.online> — здесь идёт вся работа

Разделы: Бирки, Промеры, Упаковка, Сдача, Склад, Кадры, Согласования, Отчёты,
Снабжение. Доступ к каждому — по флагам сотрудника; таб-бар прячет недоступное,
`app/middleware/erp-flow.global.ts` закрывает и прямой переход по URL.

## 3. Стек и границы

Nuxt 4 (SPA, `ssr: false`) · Vue 3 · Pinia · TypeScript · sass — фронтенд.
PHP 8 + MySQL — API в `public/api/`. Google Apps Script — legacy-бэкенд,
из которого продукт переезжает.

Режим бэкенда переключается переменной `NUXT_PUBLIC_ERP_BACKEND_MODE`
(`gas` | `sql`). **Стенд уже на `sql`, прод пока на `gas`.** Диспетчер —
`app/utils/erp-sheets.ts`: он раскидывает каждую операцию по GAS/SQL/CSV.

| Зона | Где лежит |
|---|---|
| Экраны | `app/pages/` |
| Общие компоненты ERP | `app/components/erp/` |
| Переиспользуемый UI | `app/components/ui/` |
| Утилиты (автоимпорт) | `app/utils/` |
| Хранилища | `store/` |
| API | `public/api/src/`, точка входа `public/api/index.php` |
| Схема БД | `public/api/migrations/` — **единственный каталог миграций** |
| Тесты | `tests/*.test.mjs` (контрактные), `tests/php/` (бэкенд) |
| Серверные скрипты | `scripts/` — CI их **не** выкладывает, см. грабли |

## 4. Правила, которые нарушать нельзя

**Секреты не попадают в git.** Ни паролей, ни токенов, ни ключей — ни в код, ни
в документацию, ни в комментарий к коммиту. Приватный конфиг API лежит на
сервере вне webroot. Карта доступов — `docs/onboarding/01-доступы.md`, там
описано *где искать*, а не *чему равно*.

**Прод не трогаем.** Вся работа — на стенде. Выкатка на прод — отдельное
действие с ручным подтверждением, только по явной просьбе человека.

**Реальные данные заказчика — только с разрешения.** Импорт, массовые правки,
рассылка уведомлений живым людям: спрашивай, даже если задача звучит как «сделай
всё».

**`npm run verify` перед каждым коммитом.** Красный verify — не коммитим.

**Схему базы меняем только миграцией, и только сверившись со стендом.** Таблицы
и колонки, заведённые руками на сервере, уже стоили одного сломанного раздела:
имя было занято, `CREATE TABLE IF NOT EXISTS` промолчал, экраны отдавали 500.
Перед новой миграцией смотри реальную схему стенда и бери имя с префиксом
раздела — подробности в [`docs/onboarding/03-грабли.md`](docs/onboarding/03-грабли.md),
раздел «Бэкенд и база».

**Проверяй руками то, что увидит пользователь.** Контрактные тесты читают
исходник и не ловят поведение. Мобильное приложение проверяется в мобильном
контексте с касаниями — см. `docs/onboarding/02-локальный-стенд.md`. Это не
формальность: так были пропущены три бага подряд.

## 5. Как здесь принято работать

1. **Ветка от `main`**, имя вида `codex/<что-делаешь>`. Пуш прямо в `main` не
   делаем — только через PR.
2. Правка + тест на неё. Тест формулирует **почему так, а не иначе** — см.
   `docs/onboarding/04-стиль.md`.
3. `npm run verify`.
4. Ручная проверка сценария, которого касалась правка.
5. Коммит: что сделано и **почему** это правильно. Не «fix bug», а какой баг,
   при каких условиях, чем подтверждено.
6. PR с описанием: проблема → решение → чем проверено.
7. Мердж в `main` автоматически выкатывает **стенд** и прогоняет пост-деплойную
   проверку. Прод — только вручную.

## 6. Чего делать не нужно

- Не хранить один и тот же факт в двух местах. Разъехавшиеся копии — главный
  источник багов в этом проекте (два каталога миграций, три копии проверки
  cron-токена, дублирующийся поиск по спискам — всё это уже чинили).
- Не добавлять зависимость ради одной функции.
- Не «улучшать» соседний код, о котором не просили. Нашёл проблему — скажи.
- Не подменять проверку предположением: «наверное, работает» здесь стоило
  трёх багов, найденных заказчиком.
